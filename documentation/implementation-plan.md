# Earmark 목업 화면 구현 계획

작성: 2026-11-01 · 관련 이슈: #1 · 작업 브랜치: `feature/1-workspace-mock`

API 명세가 확정되기 전, 검증 가능한 화면 단위로 구현한다. 이번 단위는 이미 워크스페이스에 들어온 사용자의 **내 작업 목록과 선택 동의 변경**이다. 이 문서는 구현 범위와 완료 조건이며, 아래 체크 항목은 검증 결과가 기록되기 전까지 완료를 뜻하지 않는다.

후속 구현은 GitFlow에 따라 이슈 등록 → 작업 브랜치 → PR 순서로 진행한다. 현재 목업 브랜치는 사용자 지시가 추가되기 전에 생성되었으므로 관련 이슈와 PR 연결을 root가 정리한다. 이슈/PR 양식과 CI 보완은 화면 구현과 별도 작업으로 관리하며, 배포 대상이 정해지기 전 CD를 구성하지 않는다.

## 기준 자료

1. 사용자의 최신 지시와 [공유 기능명세 v0.3](https://docs.google.com/spreadsheets/d/1Lv2dwjHSNSimr06ntmF7oXVtmqvNeo5aJTSLNAqNX_0/edit?usp=sharing)의 해당 도메인 행·정책결정. `차수별 정책`은 팀원 담당을 확인하는 자료이며 COPY 행 누락에 주의한다.
2. 시각·문구·배치는 [Earmark — 기타 카피 보조 서비스 디자인 v2](https://www.figma.com/design/87W9ZPWGTWqNHX7HTfQ1kZ). 로컬 안내 문서는 `UI_디자인_v3_2026-10-28.md`이며, 파일 이름과 문서 버전이 다르다.
3. 로컬 서비스 기획서 v0.4, 정책 결정사항 2026-09-17 갱신본, 기능명세 v0.3, UI 노하우 2026-10-29.
4. 제안서·기술스택·AI 기술 검토·비용 리서치는 설계 참고 자료다. 제안된 API·수치·일정을 확정 계약으로 간주하지 않는다.

검토 문서 전체와 확인 한계는 [요구사항 검토 기록](requirements-audit.md)에 있다. 정책과 디자인의 임시값이 다르면 확정 정책을 우선하고 임시값은 목업 설정으로 격리한다.

### 확정한 구현 경계

- `WorkspaceRepository`는 `loadWorkspace(signal)`과 `saveConsent(choice, signal)`을 제공한다. 목업은 `createMockWorkspaceRepository(scenario)`로 생성한다. 이 함수 이름은 FE 내부 계약이며 서버 endpoint가 아니다.
- `useWorkspace(repository, scenario)`의 결과는 `loadState`, `workspace`, `tasks`, `errorMessage`, `consent: { choice, status, errorMessage }`, `retryLoad()`, `saveConsent(choice): Promise<boolean>`, `demoScenario`다. App이 저장소를 만들고 훅 결과를 `WorkspacePage`에 전달한다.
- 로딩·취소·저장 오류는 저장소/훅에서 처리하고, 표시와 필터는 UI가 담당한다. 서버 API가 확정되면 변환 책임을 가진 실제 adapter로 목업 저장소를 교체한다.
- 처리 상태와 카피 확인 상태를 분리한다. 타브 생성 성공은 사용자가 카피를 완료했다는 뜻이 아니다(COPY-04). 이번 목록은 상태를 보여 주며, 실제 카피 완료 변경 동작은 이후 작업 공간 단계에서 구현한다.
- 화면 데이터는 예시다. 삭제·생성·작업 상세·실제 진입·다운로드·재생은 이번 범위에 없다. 미구현 동작에 성공 메시지나 실제로 이동하지 않는 활성 버튼을 제공하지 않는다.

### 비기능 완료 기준

- 접근성: 버튼·입력의 의미 있는 이름, 보이는 키보드 포커스, 선택 상태와 오류의 텍스트 안내. 모달 진입/닫기 후 포커스 이동, 키보드 이탈 방지와 Escape 동작을 확인한다. 상태를 색만으로 구분하지 않는다.
- 반응형: Figma 데스크톱 기준과 좁은 뷰포트에서 긴 파일명·긴 구간명·상태 표시가 겹치지 않는다. 주요 조작을 가리거나 가로 스크롤에 숨기지 않는다.
- 렌더링: 목록과 동의는 필요한 상태만 갱신한다. 이 화면에 파형·악보·녹음 라이브러리를 도입하지 않는다. 실제 재생 구현 시 고빈도 시간 갱신을 페이지 전체 상태와 분리한다.
- 리소스: 조회 취소·오래된 응답·중복 저장을 처리한다. 향후 파일/오디오 단계는 object URL, 이벤트, 녹음 스트림, worker의 생성·해제를 같은 경계에서 관리한다.
- 시각: Noto Sans KR UI, JetBrains Mono 숫자·시간, 오렌지 `#FF5A1F`, 따뜻한 배경 `#F6F5F2`, 1px 구분선 등 Figma 토큰을 공통으로 적용한다. 한국어를 숫자용 서체로 표시하지 않는다.

### 검증 체크리스트

- [ ] 기본 목록의 파일명·구간·시간·처리 상태·카피 상태가 fixture와 일치한다.
- [ ] 필터 변경, 전체 빈 상태, 필터 결과 없음이 구분된다.
- [ ] 처리 완료이지만 카피 미확인인 작업을 카피 완료로 표시하지 않는다.
- [ ] 로딩·조회 오류·만료 상태에서 잘못된 작업 자료나 성공 안내가 보이지 않는다.
- [ ] 동의·거부·미선택이 구분되고 선택 변경이 가능하며, 저장 실패는 기존 선택을 보존한다.
- [ ] 새로고침 시 목업 선택이 초기화되는 동작과 제한이 README/문서에 설명된다.
- [ ] 키보드만으로 필터·동의 모달을 조작하고 모달을 닫은 뒤 포커스를 되찾는다.
- [ ] 데스크톱·좁은 화면에서 겹침·잘림·가려진 조작이 없다.
- [ ] 코드 리뷰, `npm run check`, 필요한 저장소/훅 테스트 및 브라우저 시나리오 확인을 마친다.

단순 정적 문구·스타일에 구현을 복제하는 테스트를 늘리지 않는다. 비동기 조회 취소, 저장 실패 시 기존 값 유지 등 동작 계약에 집중하고, UI는 실제 브라우저로 확인한다.

현재 `npm test`는 `tests/workspace-repository.test.mjs`의 저장소 계약 테스트를 Node 24의 기본 테스트 러너로 실행한다. `npm run check`는 format → lint → test → build 순서이며 build에 TypeScript 검사가 포함된다. 저장소 테스트 통과가 브라우저·실제 API 검증을 대신하지 않는다.

공통 의존관계는 `1 → 2 → 3 → 4 → 5B → 6/7`이다. 5A 렌더러 검증은 3/4와 독립적으로 미리 수행할 수 있다. 8은 마지막에 한꺼번에 붙이는 작업이 아니라 API가 확정되는 단계마다 적용한다. 로그인/JWT·자동 구성 분석·악보 편집/이조·음표 추적·속도/믹서·YouTube·결제/커뮤니티는 별도 후속 범위다.

## 담당 구분

### 실제 팀원 담당

공유시트 `차수별 정책`의 개발 담당을 그대로 옮겼다. 기능 담당과 모든 화면의 작성자를 같은 의미로 보지 않는다.

| 팀원   | 공유시트 담당 기능                             |
| ------ | ---------------------------------------------- |
| 서지영 | ACC-02·06·07, IN-01~05, DATA-01·02·05          |
| 구민성 | SEG-01~04, REC-01~04                           |
| 국태양 | JOB-01~05, CMP-01~05                           |
| 복재환 | TAB-01~04; TAB-04는 `복재환(추후 확장성)` 표기 |

김효찬의 PM/FE 및 COPY-01~04 역할은 **제안서** 근거다. 공유시트 `카피작업` 탭에는 COPY 기능이 있지만 담당 칸이 없고, `차수별 정책`에는 네 기능이 빠져 있으므로 이 역할을 live 담당 셀에서 확인했다고 표기하지 않는다. 3차 이후 개발 담당과 정책결정 담당은 공유시트에서 공란이다.
