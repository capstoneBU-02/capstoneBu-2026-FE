# 타브 렌더러 결정 기록

작성: 2026-11-13 · 관련 이슈: [#18](https://github.com/capstoneBU-02/capstoneBu-2026-FE/issues/18) · PR: [#43](https://github.com/capstoneBU-02/capstoneBu-2026-FE/pull/43)(표시 모델과 레이아웃), [#44](https://github.com/capstoneBU-02/capstoneBu-2026-FE/pull/44)(화면 표시) · 작업 브랜치: `feature/18-tab-renderer`, `feature/18-tab-view`

완료된 작업 화면의 타브 영역을 그리는 방식과 그 근거를 기록한다. #18은 표시 모델, 레이아웃, SVG 렌더러, 타브 영역 머리, 현재 마디 표시까지 다룬다. 작업 공간 연결은 #19 B, PNG·PDF 내려받기는 #19 C에서 진행할 예정이다. 서버의 타브 형식은 아직 정해지지 않았으므로 렌더러는 목업 악보로만 검증하였다.

근거 자료는 Figma [타브 25:2](https://www.figma.com/design/87W9ZPWGTWqNHX7HTfQ1kZ?node-id=25-2), [Foundations 34:1651](https://www.figma.com/design/87W9ZPWGTWqNHX7HTfQ1kZ?node-id=34-1651)의 `Mono/Tab`(JetBrains Mono Bold 13/16), [내려받기 84:2226](https://www.figma.com/design/87W9ZPWGTWqNHX7HTfQ1kZ?node-id=84-2226)과 정책 TAB-01~04, D13이다.

## 비교 요약

저장소 밖 임시 Vite 프로젝트에서 같은 표시 모델과 같은 목업 악보(E 표준 4마디, Drop D 2마디)로 세 렌더러를 비교하였다. Chrome, 화면 폭 390·1280, 반복 10회 측정이다. 측정 당시 시스템 부하가 높아 절대값보다 상대 비교에 의미가 있다.

| 항목                     | 직접 SVG          | VexFlow 5.0.0                 | alphaTab 1.9.0                         |
| ------------------------ | ----------------- | ----------------------------- | -------------------------------------- |
| 라이선스                 | 자체 코드         | MIT, Bravura OFL              | MPL-2.0, Bravura OFL, 저작권 표기 조건 |
| 지연 로드 크기(gzip)     | 3.2 KiB           | 332.0 KiB                     | 603.4 KiB                              |
| 불러오기 / 첫 렌더(1280) | 24ms / 16ms       | 47ms / 69ms                   | 103ms / 179ms                          |
| 해머온 `2h4`             | 숫자 사이 h(시안) | 호 + h, 390에서 h가 호에 붙음 | 호 + 오선 위 h                         |
| 쉼표                     | 경로로 그린 기호  | 탭 오선에서 불가, 우회 필요   | Bravura 기본                           |
| 마디 경계                | 레이아웃 값       | stave 좌표                    | boundsLookup                           |
| 시안 일치                | 높음              | 중간                          | 중간                                   |

alphaTab은 마디가 10개를 넘으면 첫 행에 ‘♪ alphaTab.net’ 표기가 붙고, 설정으로 끌 수 없다. 내려받은 PNG·PDF에도 남는다. VexFlow는 기본 엔트리에 글꼴 6개가 base64로 들어 있어 별도 구성과 우회가 많았다. 직접 SVG는 크기, 시안 일치, 라이선스 조건, 마디 경계를 레이아웃이 직접 갖는 점에서 앞섰다. 대가는 표현 범위를 직접 늘려야 한다는 점이다. 렌더러가 표시 모델에만 의존하므로 범위가 커지면 VexFlow로 바꾸는 길이 남는다.

## 표시 모델과 adapter 경계

렌더러는 `TabScore`만 읽는다. 튜닝은 높은 줄부터 음이름과 옥타브(`E4 B3 G3 D3 A2 E2`), 마디는 구간 0초 기준 시작 시각(`startSeconds`), 악보 끝은 `endSeconds`로 표현한다. 음은 줄 번호(1이 가장 높은 줄), 프렛, 해머온, 앞 음과의 타이를 가진다. 박은 음 길이(1·2·4·8·16), 점, P.M. 여부와 음 목록을 가지며, 음 목록이 비면 쉼표다.

서버 응답은 저장소 계층의 변환 함수가 이 모델로 바꾸고, `parseTabScore`가 줄·프렛 범위, 음 길이, 마디 박 합, 타이와 해머온 연결을 검사할 예정이다. 서버 형식이 정해지기 전까지 목업은 `demoTabScores.ts`의 입력을 그대로 검사해 사용한다.

## PDF 호환 글자 규칙

svg2pdf.js는 `paint-order`, `dominant-baseline`, CSS 변수를 무시한다. 화면 SVG를 그대로 PDF로 옮길 수 있도록 아래 규칙으로 그린다.

| 규칙            | 처리                                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| 숫자 뒤 줄 가림 | 숫자와 해머온 h 앞에 흰 사각형(`#fff`). 폭은 글자 수 × 0.6em + 2                                      |
| 기준선          | 글자 중심에서 0.35em 아래로 직접 지정                                                                 |
| 굵기            | 프렛 700, 줄 이름·마디 번호·P.M.·h는 400. PDF에 등록할 굵기와 일치                                    |
| 글꼴            | SVG 루트의 `font-family` 첫 항목이 `JetBrains Mono`                                                   |
| 색              | 고정 hex. 화면 토큰 `--ink-primary`, `--ink-tertiary`, `--border-strong`, `--console-muted`와 같은 값 |
| 금지 속성       | `paint-order`, `dominant-baseline`, `style`, `class` 속성과 CSS 변수(`var()`)                         |
| 쉼표            | 경로로 그린 기호. 음악 글꼴 없음                                                                      |

흰 사각형이 보이지 않으려면 타브 영역 배경이 흰색이어야 한다. 그래서 `.panel` 배경을 `--surface-default`로 지정하였다. 배경색을 바꾸면 사각형 색도 함께 바꿔야 한다. 브라우저 테스트가 SVG 루트와 모든 하위 요소에서 금지 속성과 CSS 변수가 없음을 확인한다. 루트 `font-family` 첫 항목, 글자별 굵기, JetBrains Mono 굵기 선언(`400 700`)도 함께 확인한다.

## 현재 마디 표시

재생 위치는 플레이어와 같이 `elapsed()` 함수로 필요할 때 읽고, React 상태에 담지 않는다. 마디를 다시 계산하는 시점은 세 가지다.

| 시점                          | 처리                                                    |
| ----------------------------- | ------------------------------------------------------- |
| 재생 중                       | requestAnimationFrame마다 계산                          |
| 멈춘 상태의 위치 이동(재시작) | 렌더링 없이 일어나므로 `subscribeSeek` 알림을 받아 계산 |
| 렌더링 직후                   | 너비 변경 등으로 레이아웃이 바뀐 경우를 위해 계산       |

마디나 레이아웃이 바뀔 때만 덮개 요소의 위치와 크기를 DOM에 직접 반영한다. `subscribeSeek(listener)`는 재생 없이 위치가 바뀔 때 `listener`를 호출하고 구독 해제 함수를 반환하는 계약이다. 지금은 하네스가 이 함수를 제공하며, 플레이어의 `useSectionPlayer`가 같은 계약을 제공하도록 #19 B에서 연결할 예정이다.

`TabView`는 악보와 레이아웃에만 의존하는 memo 요소다. 재생과 위치 이동은 SVG를 다시 그리지 않으며, 브라우저 테스트가 MutationObserver로 SVG 변경이 0건인 것을 확인한다. 덮개는 `--accent-soft` 배경에 `mix-blend-mode: multiply`를 적용해 숫자 위에 겹쳐도 숫자가 흐려지지 않는다.

## 지연 로드와 실패 처리

`TabStaff`는 `lazy()`로 받는 별도 청크다. 모든 패널이 하나의 lazy 요소를 공유하므로 한 번 받은 뒤 다른 작업의 타브를 열면 기다림 없이 그린다. lazy 요소는 실패한 불러오기를 계속 기억하므로, 불러오기가 실패하면 새 lazy 요소로 교체한다. ‘다시 시도’는 오류 경계를 새로 만들어 교체된 요소를 다시 받는다. 그리기 중 오류도 같은 경계가 받아 작업 공간과 플레이어는 계속 사용할 수 있다. 실패 문구는 두 경우를 모두 포함하도록 원인을 특정하지 않는다. ‘다시 시도’를 누르면 버튼이 사라지므로 포커스를 타브 제목으로 옮긴다.

## 측정

타브 하네스를 프로덕션 빌드로 만들어 Chrome에서 측정하였다(2026-11-13, 각 3회 이상). 첫 표시는 페이지 이동부터 SVG가 보일 때까지의 시간이다.

| 항목                                | 값                                                                            |
| ----------------------------------- | ----------------------------------------------------------------------------- |
| 지연 청크 `TabStaff`                | 11.97 kB, gzip 4.85 kB                                                        |
| 패널 쪽 코드(`TabPanel`, 경계, CSS) | JS 약 2.2 kB, gzip 약 1.1 kB(압축 전 코드 기준 상한), CSS 1.0 kB, gzip 0.5 kB |
| 현재 앱 번들 변화                   | 없음. 작업 공간 연결은 #19 B                                                  |
| 첫 표시, 4마디, CPU 1배             | 346–416ms                                                                     |
| 첫 표시, 48마디, CPU 1배            | 354–371ms                                                                     |
| 첫 표시, 4마디, CPU 4배 감속        | 464–588ms                                                                     |
| 첫 표시, 48마디, CPU 4배 감속       | 505–559ms                                                                     |
| 너비 변경 후 다시 배치(1280→390)    | 1배 13–26ms, 4배 감속 29–80ms(48마디가 상한)                                  |

청크 크기는 리뷰 반영 후 다시 측정한 값이고, 시간은 리뷰 반영 전에 측정한 값이다. 첫 표시 시간은 하네스 전체(React, 글꼴, 목업 검사 포함)를 받는 시간이다. 지연 청크 요청 자체는 로컬에서 2–7ms였다. 비교 요약의 3.2 KiB(약 3.3 kB)는 비교용 시험 구현의 크기다. 이후 리듬 기호, 타이, 해머온, 현재 마디 표시, 실패 처리를 더해 실제 청크는 gzip 4.85 kB가 되었다. 작업 공간에 붙인 뒤의 실제 증가량은 #19 B에서 다시 측정할 예정이다.

| 정지 상태의 표시 | 재생 위치가 0초여도 1마디를 표시. 악보 끝 이후와 0초 이전은 표시 없음                                             |
| 실패 문구        | ‘타브를 표시하지 못했어요. 다시 시도해 주세요.’ 시안에 타브 영역 실패 상태가 없어 임시 지정                       |
| 마디 시각        | 표시 모델의 `bars[].startSeconds`. 서버 제공 방식은 협의 6                                                        |
| 범위 밖 표기     | 벤드·슬라이드·풀오프·잇단음표·박자 변경. 서버 형식이 정해지면 추가                                                |
