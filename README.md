# Earmark Frontend

음원 기반 기타 카피 보조 서비스의 프론트엔드.

## 개발환경

- Node.js 24 LTS
- npm 11
- React, TypeScript, Vite
- Oxlint, Prettier
- Husky, commitlint

의존성 버전은 `package-lock.json`으로 관리한다. 린트는 Vite 공식 템플릿의 Oxlint 구성을 사용한다.

## 실행

```bash
nvm use
npm ci
npm run dev
```

### API 실행 모드

실행 모드와 API 주소는 환경 변수로 정한다. 모든 값은 선택 사항이며, 바꿀 값만 `.env.example`을 참고해 `.env.local`에 적는다.

| 변수               | 기본값                  | 용도                                                                        |
| ------------------ | ----------------------- | --------------------------------------------------------------------------- |
| `VITE_API_MODE`    | `mock`                  | `mock`은 브라우저 메모리의 목업 저장소, `http`는 실제 API 저장소            |
| `VITE_API_BASE`    | `/api/v1`               | API 기준 주소. 같은 출처의 경로 또는 사용자 정보·쿼리·해시 없는 http(s) URL |
| `API_PROXY_TARGET` | `http://localhost:8000` | `npm run dev`와 `npm run preview`가 `/api` 요청을 넘기는 백엔드 주소        |

기준 주소가 경로이면 브라우저는 Vite 프록시를 거쳐 같은 출처로 요청하고, 세션 쿠키도 같은 출처에만 보낸다. 다른 출처의 URL이면 쿠키를 함께 보내므로(`credentials: 'include'`) 서버가 그 출처와 자격 증명을 허용해야 한다. 백엔드 세션 쿠키는 `SameSite=Lax`여서 포트만 다른 주소처럼 같은 사이트의 요청에만 실린다. 다른 사이트의 API에 보내려면 백엔드가 쿠키를 `SameSite=None; Secure`로 설정해야 하며, Safari는 그렇게 해도 다른 사이트의 쿠키를 기본으로 차단한다. 따라서 같은 출처 프록시나 같은 사이트 배포를 권장한다. `API_PROXY_TARGET`은 `VITE_` 접두사가 없어 브라우저 코드에 포함되지 않는다.

설정 값의 형식이 맞지 않으면 앱은 시작 오류 화면을 표시하고 원인을 콘솔에 남긴다.

`http` 모드는 항상 코드 입력 화면부터 시작한다. 지금은 테스터 코드 로그인, 세션 확인, 곡 올리기, 곡·구간 목록, 구간 작업의 생성·수정·처리 상태·다시 시도·멈추기, 분리 기타 음원 받기, 완료된 타브 보기, 연주 저장·목록, 연주 비교의 요청·상태·결과·다시 시도·확인 표시·재생을 실제 API에 연결했으며, 나머지 기능은 연동 단계마다 차례로 연결한다.

- 입력한 코드는 공백을 지우고 대문자로 바꿔 `POST /auth/tester-login`에 보낸다. 서버는 모르는 코드·만료 코드·폐기 코드를 같은 오류로 응답하므로 화면에는 코드 확인 문구 하나만 나온다. 예시 코드(`EM-…`)는 목업 전용이라 형식 오류로 거부된다.
- 서버는 코드의 해시만 보관하므로 설정의 마스킹 코드는 이 페이지가 보낸 값이며 메모리에만 남는다.
- 안내 확인·온보딩 완료·AI 활용 동의는 서버 API가 없어 작업 공간별로 페이지 메모리에만 기억한다. 새로고침하면 코드 입력과 안내·동의를 다시 거친다.
- 작업 공간을 열 때 `GET /workspaces/me`로 세션을 확인한다. 세션이 없거나 만료되었거나 다른 탭에서 다른 코드로 들어와 쿠키가 바뀌었으면 만료 화면을 표시한다.
- 곡 추가는 파일을 `POST /tracks/upload`에 multipart로 보낸다. 입력 종류는 `is_separated_stem`에 담고, 파일 MIME은 확장자에 맞춰 `audio/mpeg`·`video/mp4`로 바꿔 보낸다. 브라우저마다 MP3에 다른 MIME을 붙이거나 비워 두기 때문이다.
- 전송 진행률을 보여 주려고 이 요청만 `XMLHttpRequest`로 보낸다. 응답과 오류는 `fetch` 요청과 같은 `ApiError`로 바뀐다.
- 서버가 형식·길이·용량·저장 한도를 이유로 거부하면 사유별 문구를 표시한다. 프록시가 본문 크기로 거부한 413(봉투 없음)도 용량 초과로 본다.
- 화면의 작업 하나는 서버의 구간 하나이며 작업 id는 `segment_id`이다. 새 구간을 저장하면 `POST /tracks/{id}/segments`로 구간을 만든 뒤 기타 음원을 요청한다. 서버는 요청받은 처리만 하므로, 처리 상태(`GET /segments/{id}/processing-status`)에 기타 음원이 없으면 기타 음원을, 기타 음원이 준비되었는데 타브가 없으면 타브를 화면이 요청한다. 그래서 타브를 요청하기 전의 처리 중 작업은 창을 닫으면 타브가 다시 들어왔을 때 이어서 만들어진다고 안내한다. 같은 입력의 작업이 이미 진행 중이라는 409(`STEM_IN_PROGRESS`·`TAB_IN_PROGRESS`)를 받으면 처리 상태를 한 번 더 읽어 그 작업을 표시한다.
- 구간 범위는 밀리초 정수로 보낸다. 구간 이름은 서버의 이름 값으로 바꾸고 번호는 화면에만 남긴다. 서버에 없는 이름(솔로)은 이름 없이 보낸다. 튜닝은 서버가 지원하는 E 표준만 요청하며, 다른 튜닝은 요청 전에 실패한다.
- 실패한 작업은 실패한 쪽(기타 음원 또는 타브)에만 다시 시도를 보낸다. 기타를 찾지 못한 실패와 음원을 읽지 못한 실패는 다시 시도 대신 구간 다시 정하기와 다른 파일 올리기를 안내한다. 서버는 고른 구간이 무음이거나 음원 길이를 넘는 경우와 파일을 읽지 못한 경우를 같은 코드로 알린다. 멈추기는 서버가 대기 중인 작업만 받는다.
- 분리 기타 음원은 서명 주소를 받아 쿠키 없이 내려받고, 주소는 만료 60초 전까지 다시 사용한다. 받기를 취소해도 주소는 남긴다. 저장소가 CORS를 허용하지 않아 지금은 브라우저에서 받지 못한다.
- 작업 공간을 열 때와 목록을 새로 받을 때 `GET /tracks`로 곡 목록을, 구간이 있는 곡마다 `GET /tracks/{id}/segments`로 구간 목록을 받는다. 구간 목록과 처리 상태는 한 번에 4개까지 요청한다. 목록을 받는 사이에 올린 곡과 만든 작업은 목록에 없어도 유지한다.
- 이 페이지가 모르는 구간은 처리 상태를 읽어 작업으로 표시한다. 서버는 구간 번호·파트·이전 결과를 보관하지 않으므로 번호 없는 이름, ‘파트 미정’, E 표준 튜닝으로 표시하고, 이름 없는 구간은 솔로로 표시한다. 이 페이지가 만든 작업은 페이지 메모리의 번호·파트·이전 결과를 유지한다.
- 서버는 범위를 바꾸면 구간 버전을 올리고, 이름만 바꾸면 버전을 유지하고 변경 시각만 바꾼다. 다음 목록에서 버전이 오르거나 같은 버전에서 변경 시각이 늦은 구간은 바뀐 범위와 이름을 반영하고 처리 상태를 다시 읽는다. 둘 다 그대로이면 진행 중인 작업만 다시 읽고, 나머지 작업은 수정 시각 문구만 지금 시각으로 다시 계산한다.
- 멈춘 구간은 서버 목록에 남지만 기타 음원이 멈춤 상태이면 목록에서 제외한다. 이 페이지에서 멈춘 구간은 목록을 받는 사이에 멈추었어도 목록에서 빼고 기타 음원을 다시 요청하지 않는다. 멈추는 동안에도 새 요청을 보내지 않으며, 이미 보낸 기타 음원 요청은 화면이 응답을 그만 기다려도 서버의 답을 기다려 함께 멈춘다. 서버가 찾지 못한 구간은 그 목록에서만 빠지고, 다른 코드의 세션에서 돌아온 뒤의 목록에 다시 나타난다.
- 원곡 음원 API가 없어 원곡 재생과 파형은 이 페이지에서 올린 곡에만 표시한다. 새 구간 화면의 재생과 파형은 고른 파일을 그대로 사용한다.
- 완료된 작업의 타브는 `GET /tabs/{id}/result`의 음표 목록을 마디로 바꿔 그린다. 서버가 16분음표·셋잇단 격자에 놓은 박 위치를 16분음표 단위로 맞추므로 셋잇단은 가까운 16분음표에 표시한다. 같은 박의 음은 화음으로 묶고, 한 줄에 음이 둘이면 신뢰도가 높은 음을 남긴다. 마디를 넘거나 음표 하나로 나타낼 수 없는 길이는 붙임줄로 잇는다.
- 마디 시작 시각은 그 마디에서 시작하는 음들의 시각과 박 위치로 정하고, 음이 없는 마디는 앞뒤 마디 사이에 고르게 놓는다. 못갖춘마디는 0초에서 시작한다. 바꿀 수 없는 결과(4분음표 단위가 아닌 박자 등)는 ‘타브를 표시하지 못했어요’로, 준비되지 않은 타브와 응답 오류는 ‘타브를 불러오지 못했어요’로 안내한다.
- 연주 저장은 `POST /segments/{id}/performances`에 파일(`audio_file`)과 입력 방식(`source`: `RECORDING`·`UPLOAD`)을 multipart로 보낸다. 서버는 파일 이름의 확장자로 형식을 가리고 MIME은 확장자가 없을 때만 본다. 올린 파일은 이름을 그대로 두고 곡 추가처럼 확장자에 맞춘 MIME으로, 녹음은 `take.wav`(`audio/wav`)로 보낸다. 업로드 창은 전송 진행률을 표시하고, 50MB를 넘는 파일은 길이를 읽기 전에 거부한다.
- 서버가 연주를 거부하면 용량 초과는 용량 문구를, 입력 오류(지원하지 않는 형식, 빈 파일, 요청 값 오류)는 ‘이 파일은 연주로 사용할 수 없어요’를 표시한다. 구간을 찾지 못하면 작업을 찾을 수 없다고 안내한다.
- 완료된 작업을 열면 `GET /segments/{id}/performances`로 그 구간의 연주를 최신순으로 받는다. 서버는 연주 길이와 최근 비교를 보내지 않으므로, 길이는 이 페이지에서 저장한 연주에만 남고 연주는 비교 기록 없이 표시한다.
- 저장한 연주는 바로 `POST /performances/{id}/comparisons`로 비교를 요청한다. 서버가 같은 연주의 끝난 비교를 다시 쓰면(200) 그 비교를 연다. 비교를 시작하지 못하면 연주는 저장됐다는 안내를 표시한다. 목록에서 고른 연주는 최근 비교를 알 수 없어 비교하지 않은 연주로 표시하고 비교하기로 요청한다. 이미 비교 중이라는 거부에는 비교 id가 없어 진행 중인 비교를 이어 보지 못하고 안내만 표시한다.
- 비교 상태는 `GET /comparisons/{id}`로 2.5초마다 읽는다. 응답에 없는 단계는 대기로, 다시 시도 직후 남아 있는 실패 단계도 대기로 표시한다. 실패한 비교는 실패한 단계에만 실패를 표시하고, 남은 횟수가 있으면 `POST /comparisons/{id}/retry`로 다시 시도한다. 상태를 읽지 못해도 진행 중인 비교는 계속 상태를 읽는다.
- 끝난 비교는 `GET /comparisons/{id}/result`의 구간을 초 단위로 바꿔 표시한다. 비교할 수 없는 연주는 서버의 일곱 가지 사유별 문구를 표시하며, 기준 음원의 음을 또렷하게 읽지 못한 경우는 연주 탓이 아니므로 다른 구간을 안내한다.
- 다시 들어볼 곳의 확인 표시는 `PATCH /comparisons/{id}/regions/{region_id}`로 저장한다. 저장하지 못하면 표시를 되돌리고 안내한다.
- 비교 재생은 `GET /comparisons/{id}/playback`의 서명 주소로 기준 음원과 연주를 받는다. 주소는 음원마다 만료 60초 전까지 다시 쓰고, 403이면 한 번 다시 받는다. 주소가 없는 음원은 재생할 수 없는 음원으로 표시한다. 분리 기타 음원처럼 저장소가 CORS를 허용하기 전에는 브라우저에서 받지 못한다.
- 서버가 카피 상태를 보관하지 않아 카피 완료 표시와 이전 결과의 카피 상태를 보여 주지 않는다. 구간 수정 안내도 카피 상태를 빼고 이전 구간이 이전 결과 목록에 남는다고만 알린다. 도움말의 자주 묻는 질문에도 카피 완료 문장을 넣지 않는다.
- 로그아웃 API가 없어 '나가기'는 화면만 코드 입력으로 바꾸며 세션 쿠키는 남는다.

## 명령어

| 명령어                 | 기능                                                   |
| ---------------------- | ------------------------------------------------------ |
| `npm run dev`          | 개발 서버 실행                                         |
| `npm run typecheck`    | TypeScript 타입 검사                                   |
| `npm run lint`         | 코드 검사                                              |
| `npm run format`       | 코드 포맷 적용                                         |
| `npm run format:check` | 코드 포맷 검사                                         |
| `npm test`             | 목업 저장소·API 공통 계층 단위 테스트                  |
| `npm run test:browser` | 진입·온보딩·설정·도움말·작업 공간 브라우저 회귀 테스트 |
| `npm run build`        | 타입 검사 및 배포 빌드                                 |
| `npm run preview`      | 빌드 결과 확인                                         |
| `npm run check`        | 포맷·린트·테스트·타입·빌드 검사                        |

빌드 결과는 `dist/`에 생성된다.

### 브라우저 회귀 테스트

```bash
npx playwright install chromium
npm run test:browser
```

Playwright가 `127.0.0.1:4174`에 테스트용 Vite 서버를 실행하고 Chromium 한 종류로 검증한다. 이미 설치한 Chrome을 쓰려면 `PLAYWRIGHT_CHANNEL=chrome npm run test:browser`로 실행할 수 있다. CI는 검사 작업과 브라우저 작업을 나누고, 브라우저 작업은 `npx playwright install --with-deps chromium` 후 같은 테스트 명령을 네 조각(`--shard=1/4`부터 `--shard=4/4`)으로 나누어 동시에 실행한다. 각 조각의 테스트 제한은 12분, 설치와 실패 보고서 업로드를 포함한 작업 제한은 20분이다. WebKit은 `npx playwright install webkit` 후 `npm run test:browser:webkit`으로 로컬에서 실행하거나, GitHub Actions의 `CI` 수동 실행에서 `browser=webkit`을 선택해 네 조각으로 시험한다. push·PR에서는 Chromium만 실행한다. 수동 WebKit 실행은 성공해도 조각별 HTML 보고서를 7일 보관한다. Linux용 Playwright WebKit은 Safari·iOS 실기기 검증을 대신하지 않는다. 터치 입력 7개는 Chromium 전용 도구를 사용하므로 WebKit에서 건너뛴다.

`tests/browser/`는 실제 `App`과 `useWorkspace`·`WorkspacePage`를 StrictMode에서 렌더하고 저장소 응답 시점만 제어한다. 코드 진입·온보딩 세 선택·재방문·다른 코드의 작업 격리, 미완료 안내 재개, 만료 복구, 제출·저장 중복과 늦은 응답을 검증한다. 설정과 목록의 동의 공유·필터 보존, 뒤로/앞으로 이동, 나가기 후 기록 격리, 도움말 키보드·포커스, 읽기 전용 안내와 작업 불가 상태도 확인한다. 기존 동의 창의 오류 초기화·네이티브 닫기·포커스 복귀·텍스트 드래그 회귀도 유지한다. 곡 추가는 파일 형식·길이 판정을 가짜 검사기로 제어한다. Playwright의 Chromium에는 MP4 코덱이 없을 수 있기 때문이다. 실제 `<audio>` 검사는 `tests/fixtures/media/tone-2s.mp3`(2초 사인파, ffmpeg로 생성)와 손상 파일로만 확인한다. 새 구간은 입력 검증·경계값, 생성 중 잠금·실패 후 재시도·만료, 작성 중 행의 유지·삭제, 파일 바꾸기 확인과 입력 유지 범위를 검증한다. 테스트 화면은 개발 서버 전용이며 배포 빌드에 포함되지 않는다. 실패 스크린샷·trace는 `test-results/`, HTML 결과는 `playwright-report/`에 생성된다.

## 구현 범위와 내 작업 목록

Figma의 `Earmark — 기타 카피 보조 서비스 디자인 v2`를 기준으로, 작업 공간에 진입한 이후의 **내 작업 목록·빈 상태·선택 AI 활용 동의**를 구현한다. 처리 상태 필터와 곡별 목록 펼치기·접기, 동의 저장·변경을 확인할 수 있다. 생성 완료와 사용자가 확인한 카피 완료는 별도로 표시한다.

## 테스터 코드 진입과 첫 안내

기본 주소는 코드 입력 화면이다. 신규 코드는 자료·접근 안내(1/2), 선택 AI 활용 동의(2/2)를 거쳐 내 작업으로 이어진다. 안내 확인은 동의와 별도로 기록한다. 안내만 확인한 뒤 다시 진입하면 2/2부터 재개하며, 동의·거부 저장 성공 또는 명시적인 '나중에 정할게요' 선택 뒤에만 온보딩을 완료한다. '나중에'는 미선택을 유지한다. 완료한 같은 코드의 재방문은 안내를 건너뛰고 기존 작업·선택으로 돌아온다.

다음 코드만 허용하는 **메모리 목업**이다. 실제 발급 코드·인증·서버 권한 검증은 제공하지 않는다.

| 예시 코드      | 초기 상태                                              |
| -------------- | ------------------------------------------------------ |
| `EM-NEW1-0001` | 신규, 빈 작업 공간, 안내 미확인·동의 미선택            |
| `EM-7K2P-9Q4M` | 재방문, 기존 작업 4개, 안내 완료·동의 거부             |
| `EM-NEW2-0002` | 별도의 신규 빈 작업 공간, 이전 코드의 작업·선택과 분리 |

코드 allowlist는 `src/app/demoConfig.ts`의 개발용 fixture다. 모르는 코드는 차단하며 서버의 코드 형식 regex, 발급 규칙, 실패 횟수나 제한 시간은 정의하지 않는다. 제출한 코드를 URL·브라우저 저장소·콘솔에 기록하지 않고, 실제 API 요청·쿠키·토큰을 만들지 않는다. 같은 앱 수명 안에서만 코드별 작업 공간과 안내·동의 상태를 유지한다. 새로고침·새 탭에서는 예시의 초기 상태로 돌아온다. 데이터 유지·인증 보안을 검증하는 실제 서버 구현이 아니다.

코드 진입 후 곡 추가와 구간 작업으로 이어진다. 파일은 현재 메모리에서 처리하며 서버에 업로드하지 않는다.

## 설정과 도움말

사이드바 설정에서 마스킹된 테스터 코드, 현재 AI 활용 선택과 이용 안내를 확인할 수 있다. '선택하기/변경하기'는 기존 동의 창과 같은 저장소를 사용한다. 설정과 목록을 오가도 목록을 다시 조회하거나 작업 필터·곡 펼침 상태를 초기화하지 않는다. '나가기'는 코드 입력으로 돌아가 현재 세션의 요청을 취소한다. 같은 앱 메모리에 있는 코드별 자료와 동의는 유지하며, 다른 코드로 들어오면 해당 코드의 작업 공간만 표시한다.

도움말 메뉴는 자주 묻는 질문, 이용 안내 다시 보기, 문의 안내를 연다. 안내를 다시 열고 닫는 동작은 안내 확인·동의·온보딩 완료 상태를 바꾸지 않는다. 문의 채널과 개인정보 처리방침 URL은 미정이므로 가짜 연락처나 외부 링크를 넣지 않았다. **자료 삭제 요청 안내는 읽기 전용**이다. 실제 요청 전송·접수·자료 삭제·코드 차단을 수행하지 않는다.

화면 이동은 `navigation.ts`에 정의한 목록·설정·작업·새 구간·구간 수정 및 접근 오류 화면만 허용하고, 새 라우터 의존성 없이 브라우저 뒤로/앞으로 이동을 지원한다. URL에는 알려진 목업 선택자와 화면 종류만, `history.state`에는 현재 세션을 구분하는 무작위 표식만 기록한다. 제출 코드·동의 값·작업 데이터는 기록하지 않는다. 다른 세션의 기록은 현재 세션의 기본 화면으로 정리하며, 진입 전이나 나간 뒤에는 과거 화면 기록으로 진입을 건너뛸 수 없다. 이 처리는 실제 서버 인증·권한 검사를 대신하지 않는다.

작업 없음과 다른 작업 공간의 작업은 같은 안내를 보여 주고 '내 작업으로' 복귀한다. 참조된 작업의 식별자나 내용을 노출하지 않는다. 구현 범위와 정책 근거는 [설정·도움말 계획](documentation/settings-support-plan.md)을 참고한다.

## 곡·구간 작업 모델과 작업 공간

작업 공간은 **곡 → 구간 작업** 구조다. 곡은 표시 이름·파일 이름·입력 종류(원곡 / 분리된 기타 음원)·길이를 가지고, 작업은 곡 id·파트·튜닝을 참조한다. 사이드바는 곡 목록을 기준으로 구간을 묶는다. 이 모델은 화면 도메인이며 API 응답 형태를 정하지 않는다.

내 작업 목록 행이나 사이드바 구간을 누르면 `?view=task&task=<작업 id>`로 이동하고, 작업 상세는 목록과 별도로 조회한다. 작업 id는 영문 소문자·숫자·하이픈 64자 이하만 허용한다. 주소로 들어온 id와 목록·사이드바에서 넘긴 id 모두 형식이 다르면 저장소에 요청하지 않고 `task-not-found` 안내로 정리한다. 없는 작업과 다른 작업 공간의 작업은 같은 오류로 처리해 같은 안내를 보여 준다. 목업은 없는 작업만 확인하며, 다른 작업 공간의 작업에 서버가 같은 오류를 응답하는지는 실제 API 연동 때 확인할 예정이다. 조회 중 다른 작업으로 이동하면 이전 요청을 취소하고 늦게 도착한 응답은 무시한다. 같은 작업을 다시 열 때도 이전 결과를 재사용하지 않고 새 조회를 기다린다. 작업 조회에서 이용 기간 종료가 확인되면 목록 조회와 같은 만료 화면으로 작업 공간 전체를 가리며, 그 뒤에 도착한 목록 응답은 만료 화면을 바꾸지 않는다. 목록을 불러오지 못해 '다시 시도'를 누르면 주소의 작업도 함께 다시 조회한다.

목록은 처음 불러온 뒤에도 서버의 작업 상태를 따라간다(#28). 탭이 다시 보이거나 창이 포커스를 되찾으면 목록을 새로 받는다. 대기·진행 중인 작업이 있는 동안에는 3초 간격의 재조회가 이어지며, 간격과 중단 규칙은 열린 작업의 재조회와 같다. 숨겨진 탭에서는 요청하지 않는다. 새 목록은 작업·곡 id별로 합치므로 펼친 곡, 선택한 작업, 포커스가 유지된다. 재조회가 실패하면 보이던 목록을 안내 없이 유지하고, 이용 기간 종료가 확인되면 만료 화면으로 바꾼다. 요청 중 화면을 떠난 구간 수정은 취소되지 않고 그 결과가 목록에 들어온다. 열린 작업 화면은 목록의 상태가 자기와 다르면 작업을 다시 조회한다. 3초는 임시값이며 서버의 상태 알림 제공 여부가 정해지면 다시 정할 예정이다.

작업 공간은 원곡·분리 기타의 파형과 재생 바, 처리 단계, 완료된 타브를 연결한다. 같은 구간에서 트랙을 바꾸거나 파형으로 위치를 이동하고 반복 재생할 수 있다. 음원 불러오기·출력 재개 실패는 오류 안내와 재시도를 제공한다. 분리 기타를 불러오지 못해도 준비된 원곡으로 전환할 수 있다.

대기·기타 분리·타브 생성·완료·실패·기타 없음 상태를 구분한다. 진행률을 받지 못한 처리 중 상태는 ‘진행률 확인 중’으로 표시하고 임의의 백분율을 만들지 않는다. 멈추기·재시도는 중복 요청을 막고, 네이티브 다이얼로그 닫힘이나 재조회로 버튼이 사라지는 경우의 복귀를 처리한다.

완료 작업에는 SVG 타브, 현재 마디 표시, 카피 완료 선택·해제, PNG·벡터 PDF 내려받기가 있다. 음원 오류가 있어도 타브를 보고 내려받을 수 있다. 렌더러의 지원 표기와 출력 방식은 [타브 렌더러 결정](documentation/tab-renderer-decision.md)을 참고한다. 목업 타브는 구간 길이에 맞춘 데모이며 실제 음원을 채보한 결과가 아니다.

구간 수정 후 이전 결과에는 순번·이름·범위·파트·튜닝·비교 수·카피 상태를 최신순으로 표시한다. 현재 모델은 요약 정보만 보관하며 이전 음원·타브·비교 기록 상세의 재열람은 제공하지 않는다. 비교 횟수 fixture는 연주 비교 기능의 구현 완료를 뜻하지 않는다.

## 다섯 번째 구현: 곡 추가와 음원 파일 검사

사이드바의 `+`, 빈 화면의 '파일 선택', 빈 화면 카드에 끌어다 놓은 파일로 곡 추가 창을 연다. 놓을 수 없는 곳으로 파일을 끌면 커서가 놓을 수 없음을 표시한다. 입력 종류(원곡 / 분리된 기타 음원)와 파일 하나를 고르면 브라우저 안에서 형식, 용량, 길이를 확인한다. 목업 모드에서는 파일을 전송하지 않는다. '다음'을 누르면 목업 저장소가 곡을 현재 세션 메모리에 추가하고 `?view=new-section&song=<곡 id>`로 이동해 바로 구간을 정한다.

- 확장자와 MIME을 함께 확인한다. MIME이 비어 있거나 `application/octet-stream`이면 확장자로 판단한다. 허용 형식이 아니면 디코딩하지 않고 형식 오류를 보여 준다. 형식이 맞아도 50MB를 넘으면 길이를 읽지 않고 용량 안내를 보여 준다. 서버와 같은 순서(형식, 용량, 길이)다.
- 길이는 `<audio>` 메타데이터로 읽는다. 재생할 수 없으면 손상 파일 안내를 보여 준다. 제한 시간 안에 읽지 못하면 시간 초과 안내와 '다시 확인'을 보여 주며, 같은 파일의 길이를 다시 읽는다. 길이는 서버처럼 밀리초로 반올림해 300,000ms를 넘으면 거부한다. 거부한 파일의 길이는 초 단위로 올림해 표시하므로 05:00을 넘는 값으로 보인다. 확인에 쓴 object URL은 결과와 관계없이 바로 해제한다.
- MP4는 오디오 트랙 유무를 직접 확인하지 않고, 브라우저가 메타데이터를 읽을 수 있는지로 판단한다. 영상만 있는 MP4가 통과할 수 있고, 브라우저 코덱 지원에 따라 결과가 달라질 수 있다.
- 브라우저는 MIME을 대개 확장자로 정한다. 그래서 다른 형식 파일의 확장자만 `.mp3`로 바꾸면, 브라우저가 재생할 수 있는 한 통과한다. 가변 비트레이트 MP3의 길이는 메타데이터 시점의 추정값이라 5분 경계 근처에서 몇 초 어긋날 수 있다. 클라이언트 검사는 빠른 안내용이며 최종 판정은 서버가 다시 한다. 서버는 파일을 직접 읽어 길이를 다시 재므로 여기서 통과한 파일도 거부될 수 있다. 목업 저장소도 형식, 용량, 길이를 다시 확인한다.
- 일부 모바일 브라우저는 문서에 붙지 않은 미디어의 `preload`를 무시할 수 있어, 길이 확인은 `load()`를 직접 호출해 시작한다. iOS Safari 실기기 동작은 아직 확인하지 않았다.
- 오류 파일은 '다음'으로 진행할 수 없고 '파일 바꾸기'로 다시 고른다. 길이 확인 시간 초과는 '다시 확인'으로 같은 파일을 다시 확인할 수도 있다. 여러 파일을 한꺼번에 놓으면 하나만 올리라고 안내한다. 창을 닫으면 선택한 파일과 입력 종류를 버리고 창을 연 버튼으로 포커스를 돌려준다. 모바일 서랍에서 열었다면 메뉴 버튼으로 돌려준다. 추가 중에는 창을 닫을 수 없고, 창 아래 안내 자리에 전송 진행률('파일 올리는 중 42%')을 보여 준다. 전송이 끝나고 서버 응답을 기다리는 동안은 '파일 확인 중'으로 바뀐다. 실패하면 선택을 유지한 채 사유를 안내한다. 형식·길이·용량 사유면 같은 파일이 다시 거부되므로 다른 파일을 고를 때까지 '다음'을 막고, 저장 한도 초과나 그 밖의 실패는 같은 파일로 다시 시도할 수 있다.
- 허용 형식·최대 용량·최대 길이·확인 제한 시간은 `src/features/add-song/uploadPolicy.ts` 한 곳에 둔다. 안내 문구와 파일 선택 창의 `accept`도 이 설정에서 만든다. 형식, 50MB, 5분은 백엔드의 업로드 제한에 맞춘 값이며, 기획 정책(D08, IN-01~05)은 아직 확정되지 않았다.
- 화면 밖에 떨어진 파일은 브라우저가 열지 않도록 막는다. 세션이 메모리에만 있어 페이지를 벗어나면 작업 공간이 사라지기 때문이다.

## 여섯 번째 구현: 새 구간 입력과 검증

사이드바 곡 아래의 '구간 추가'나 곡 추가 직후 새 구간 화면이 열린다. 이름(정해진 이름 + 번호), 시작·끝(`00:00.0`), 파트(리듬 / 리드 기타), 튜닝을 정하고 '타브 만들기'를 누르면 목업 저장소가 '대기' 상태의 작업을 만들고 그 작업 공간으로 이동한다. 시작·끝은 직접 입력하거나 파형에서 끌어 정한다.

- `0 ≤ 시작 < 끝 ≤ 곡 길이`이고 구간 길이가 최대 길이 이하일 때만 제출할 수 있다. 시간 형식, 끝이 시작보다 앞섬, 곡 길이 초과, 최대 길이 초과를 각각 다른 문구로 알린다. 오류는 아이콘과 문장으로 입력 아래에 보이고, 해당 입력의 `aria-invalid`·`aria-describedby`로 연결한다. 오류는 입력을 벗어난 뒤나 제출을 시도한 뒤에만 보인다. 오류가 있을 때 제출하면 모든 오류를 보이고 첫 오류 입력으로 포커스를 옮긴다.
- 시간은 내부에서 0.1초 단위 정수로 다뤄 경계(예: 30.0초) 비교에 소수 오차가 없다. 입력을 벗어나면 `00:42.1` 형태로 정리한다. 곡 길이는 0.1초 단위로 내림해 끝 시간의 상한으로 쓴다.
- 전체 파형에서 끌면 새 범위를 정하고, 선택 영역 안쪽을 끌면 길이를 유지한 채 옮긴다. 경계의 핸들은 끌거나 화살표·Page Up/Down·Home·End 키로 조절하며, 확대 파형의 핸들로 세밀하게 맞춘다. 두 핸들의 안쪽 판정 영역(각 6px)보다 좁은 구간은 안쪽을 누르면 옮겨지고, 핸들은 경계 바깥쪽을 잡아 조절한다. 손가락이나 펜으로 잡은 핸들은 옆으로 6px 이상 움직인 뒤부터 따라간다. Alt·Ctrl·Meta와 함께 누른 키는 브라우저에 넘기고, 슬라이더 값은 `1분 5.8초` 형식으로 읽힌다(#16, #25).
- 번호는 같은 곡에서 쓰지 않은 가장 작은 번호를 기본값으로 채운다. 비우면 번호 없이 저장하고, 앞의 0은 무시한다(`07` → `7`). 같은 이름을 직접 다시 입력하는 것은 막지 않는다(SEG-03/04 미확정).
- 구간 수정에서 이름을 바꾸면 같은 규칙으로 새 이름의 번호를 채우고, 원래 이름으로 돌아오면 원래 번호를 되살린다. 번호는 제안한 번호이거나 원래 이름의 원래 번호일 때만 이름을 따라 바뀌며, 그 밖에 입력하거나 비운 번호는 이름을 바꿔도 유지한다. 정책에 없는 이름·파트·튜닝은 첫 항목으로 바꾸고, 원래 값을 파형 위 안내에 함께 표시한다(#29, 안내 문구는 임시).
- 작성 중인 입력은 곡별로 메모리에 보관한다. 다른 화면에 다녀와도 유지되고, 사이드바에 '새 구간' 행으로 보인다. '취소'를 누르거나 작업을 만들면 버린다. 아무것도 바꾸지 않은 화면은 떠나면 행이 사라지고, 제출을 시도해 보였던 오류도 함께 지운다. 새로고침하면 초기화된다.
- '파일 바꾸기'는 확인 창을 먼저 띄운다. 확인하면 곡 추가 창이 열리고, 새 파일을 추가하면 새 곡으로 이동한다. 이름·번호·튜닝은 유지하고 범위와 파트는 다시 고른다. 곡 추가 창은 바꾸기 전 곡의 입력 종류로 시작한다. 기존 곡과 이미 만든 작업은 그대로 남는다(IN-05 미확정, 새 곡으로 추가하는 방식을 임시로 택함). 확인 창이나 곡 추가 창을 닫으면 입력이 그대로이고 포커스는 '파일 바꾸기'로 돌아온다.
- 만드는 중에는 입력과 '취소'·'파일 바꾸기'를 잠그고 중복 제출을 막는다. 실패하면 입력을 유지한 채 안내하고, 제출한 입력이나 버튼으로 포커스를 돌려줘 바로 다시 시도할 수 있다. 만드는 동안 연 곡 추가·도움말 창은 새 작업으로 이동해도 닫지 않는다. 화면을 떠나면 요청을 취소하므로, 응답을 기다리는 앞 요청이 있어도 다른 곡의 새 구간은 바로 보낸다. 실제 API에서는 취소 전에 서버가 이미 작업을 만들었을 수 있으므로, 같은 요청의 중복 생성을 막는 방법(멱등 키 등)을 API 계약에서 정해야 한다. 이용 기간이 끝났다는 응답이면 만료 화면으로 바꾸고 포커스를 본문으로 옮긴다.
- 최대 길이·이름 목록·번호 범위·파트·튜닝은 `src/features/new-section/sectionPolicy.ts` 한 곳에 둔다. 화면 문구와 목업 저장소 검사도 이 설정을 따른다. 목업 저장소는 0.1초 단위가 아닌 시간을 반올림하지 않고 거부한다. 최대 30초(D11)와 튜닝 3종(IN-04)은 디자인 기준 임시값이며, 최소 길이는 아직 정하지 않아 0.1초부터 허용한다.
- 새 작업의 '대기' 상태는 회색 점으로 표시하고 '진행 중' 필터에 포함한다. 작성 중인 새 구간 행은 회색 테두리 점으로 구분한다.

### 목업 상태 확인

`npm run dev`를 목업 모드(기본값)로 실행한 뒤 개발 서버 주소에 다음 쿼리를 붙인다. `http` 모드에서는 `demo`·`access` 선택자를 읽지 않고 코드 입력 화면부터 시작한다.

| URL 쿼리              | 상태                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------- |
| 없음                  | 테스터 코드 입력, 허용 코드로 신규/재방문 진입                                              |
| `?demo=workspace`     | 기존 작업 4개와 미선택 동의 배너 직접 보기                                                  |
| `?demo=empty`         | 작업이 없는 상태                                                                            |
| `?demo=error`         | 첫 목록·첫 작업 조회 실패, 다시 시도하면 정상                                               |
| `?demo=expired`       | 작업 공간 이용 종료, 작업 내용은 표시하지 않음                                              |
| `?demo=consent-error` | 동의 저장 실패, 기존 선택을 유지                                                            |
| `?demo=task-states`   | 작업 상태 7개. 대기, 진행, 완료, 타브 생성 실패와 다시 시도 소진, 기타 분리 실패, 기타 없음 |

알려진 `demo` 값만 목록 미리보기를 연다. 알 수 없는 값으로는 코드 진입을 건너뛸 수 없다. 목록의 세션 만료 상태에서는 '코드 다시 입력'으로 돌아가 새 진입을 할 수 있다.

설정·작업 공간·작업 불가 화면의 직접 미리보기:

| URL 쿼리                                                 | 상태                                                                                                  |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `?demo=workspace&view=settings`                          | 설정, 미선택 AI 활용 상태                                                                             |
| `?demo=workspace&view=task&task=task-verse`              | 원곡 입력 완료 작업(`task-solo` 진행 중, `task-intro` 분리 기타 입력 실패, `task-chorus` 기타 없음)   |
| `?demo=workspace&view=task-not-found`                    | 작업을 찾을 수 없는 상태                                                                              |
| `?demo=workspace&view=task-inaccessible`                 | 다른 작업 공간의 작업 접근 불가 상태, 위와 동일한 안내                                                |
| `?demo=workspace&view=new-section&song=song-neon-harbor` | 새 구간 입력 화면                                                                                     |
| `?demo=workspace&view=edit-section&task=task-chorus`     | 기타를 찾지 못한 작업의 구간 다시 정하기 화면                                                         |
| `?demo=workspace&view=edit-section&task=task-solo`       | 진행 중인 작업의 수정 주소. 타브를 만드는 중이라는 안내. 이전 결과가 있으면 다시 만드는 중이라고 안내 |
| `?demo=workspace&view=song-not-found`                    | 곡을 찾을 수 없는 상태. 형식이 다른 곡 id도 이 안내로 정리                                            |

`view`만으로 코드 진입·온보딩을 우회할 수 없다. 직접 미리보기는 명시적인 개발용 `demo` 선택자를 함께 사용한다. 새 세션에서 이전 세션의 브라우저 기록을 만나면 기본 화면을 표시한다.

진입 오류는 허용 코드를 입력한 뒤 다음 fixture 쿼리로 확인한다.

| URL 쿼리                  | 상태                                                         |
| ------------------------- | ------------------------------------------------------------ |
| `?access=invalid`         | 무효 코드 응답                                               |
| `?access=code-expired`    | 코드 사용 기간 만료. 세션 만료 배너와 구분                   |
| `?access=revoked`         | 코드 사용 중지                                               |
| `?access=limited`         | 첫 응답에서 제한 상태. 명시적인 '다시 확인' 후 정상 응답     |
| `?access=network`         | 코드 확인 실패, 입력 수정·재시도 가능                        |
| `?access=session-expired` | 세션 만료 안내 배너, 허용 코드로 다시 진입 가능              |
| `?access=consent-error`   | 온보딩 동의 저장 실패. 2/2 유지, '나중에'로 미선택 진행 가능 |

제한 fixture는 서버 제한 응답과 해제 응답을 재현한다. 클라이언트의 실제 실패 횟수 누적·타이머·자동 해제 정책은 구현하지 않는다. 다른 오류 fixture는 해당 오류를 반복해서 보여 주며 새로고침하면 초기 상태로 돌아온다.

조회·저장에는 짧은 고정 지연을 두어 로딩과 저장 중 상태도 확인할 수 있다. 목업 데이터는 네트워크 요청이나 브라우저 저장소를 사용하지 않는다. 동의 선택은 현재 앱의 메모리에만 남고 새로고침하면 해당 fixture 초기값으로 돌아온다. 동의를 거부해도 목록 사용을 제한하지 않는다. fixture 작업은 처음 상태를 유지한다. 세션에서 만들거나 바꾼 작업만 목업 대기열에 따라 대기, 기타 분리, 타브 생성, 완료 순으로 진행한다. 실제 AI 처리는 수행하지 않는다.

`src/app/demoConfig.ts`의 보관 기간·테스터 코드 형식은 디자인 확인을 위한 임시 값이다. 제품 정책이나 API 명세의 확정값이 아니다. `uploadPolicy.ts`의 업로드 제한은 백엔드 구현에 맞췄으나 제품 정책으로 확정된 값은 아니다.

### 디자인 폰트

Figma에서 확인한 Noto Sans KR 400·500·700(UI), JetBrains Mono 400·500·700(시간·코드·타브 숫자), Geist 600(로고)을 로컬 WOFF2로 제공한다. Figma에서는 글꼴 이름과 굵기를 확인했고, 폰트 파일은 공식 Google Fonts 배포본을 사용한다. 세 글꼴은 SIL OFL 1.1로 배포된다.

Noto Sans KR은 한글 완성형 11,172자와 자모·라틴을 포함하는 공식 유니코드 부분집합을 유지한다. `unicode-range`에 따라 화면에 필요한 파일만 요청하며, 전체 한글 파일을 미리 내려받지 않는다. JetBrains Mono와 Geist는 현재 사용 범위인 라틴 부분집합만 포함한다. `font-display: swap`으로 글자가 보이지 않는 대기를 피하고, 기존 고정 줄 높이를 유지한다. 폰트 요청은 모두 앱과 같은 출처로 향하며 런타임 Google Fonts 요청은 없다.

글꼴 출처·굵기·용량·검증 방법은 [폰트 출처](src/assets/fonts/SOURCES.md), 파일별 원본 URL과 SHA-256은 [폰트 목록](src/assets/fonts/sources.json)에 기록한다. 배포물에는 `public/fonts/`의 라이선스 원문을 함께 포함한다.

### API 연결 경계

`src/features/access/repository.ts`의 `AccessRepository`는 코드 검증·진입 결과·안내 확인·온보딩 완료를, `src/features/workspace/repository.ts`의 `WorkspaceRepository`는 목록·작업 조회, 동의 저장, 곡 추가, 구간 작업 생성·변경, 멈추기, 다시 시도, 원곡·분리 기타 음원과 타브 불러오기를 담당한다. 카피 완료 저장은 카피 상태를 보관하는 저장소(목업)만 맡는다. `main.tsx`는 시작할 때 `src/app/repositories.ts`로 실행 모드에 맞는 저장소를 한 번 선택해 `App`에 넘긴다. 목업 저장소와 실제 저장소는 각각 별도 파일 조각으로 나뉘어 해당 모드에서만 내려받는다. 연주 비교 저장소(`ComparisonRepository`)는 `AppRepositories.comparison`으로 넘기며, http 모드는 실제 저장소를, 목업 모드는 null을 넘겨 열린 작업 공간을 바탕으로 한 목업을 사용한다. 세션이 열린 뒤에만 `WorkspaceSession`을 마운트하며, 온보딩과 목록에서 같은 작업 공간 저장소를 사용한다. 목록에서 바꾼 동의도 같은 코드의 다음 진입 결과에 반영한다.

실제 저장소와 응답 변환은 기능별로 차례로 연결한다. 공통 HTTP 계층은 `src/api/`에 있고, 기능별 연동은 `apiTypes.ts`(서버 요청·응답 타입, snake_case 그대로), `adapter.ts`(응답 검사와 화면 모델 변환), `httpRepository.ts`(저장소 구현과 서버 오류 코드 연결)로 나눈다. `http.ts`는 백엔드 응답 봉투를 풀고 실패를 `ApiError`(상태, 코드, 메시지, 세부 정보, 추적 id)로 바꾼다. 서버 코드가 없는 실패는 응답이 없으면 `NETWORK`, 봉투 없는 오류 응답이면 `HTTP_<상태>`, 봉투나 `data` 모양이 다른 성공 응답이면 `INVALID_RESPONSE`로 표시한다. 백엔드도 코드를 정하지 않은 상태(405 등)에는 봉투 안에 `HTTP_<상태>`를 담으므로, 이 접두사만으로 봉투 유무를 판단하지 않는다. 취소한 요청은 `AbortError`로 끝나며, 공통 계층에는 다시 시도와 시간 제한이 없다. form 본문 요청에 `onUploadProgress`를 넘기면 `fetch`가 알려 주지 않는 업로드 진행률을 받으려고 `XMLHttpRequest`(`upload.ts`)로 보내며, 응답 해석은 같은 경로를 거친다. 요청마다 `X-Trace-Id`를 보내고 백엔드는 받은 값을 응답의 추적 id로 사용한다. 응답에 추적 id가 없으면 보낸 값을 `ApiError`에 담는다. `guards.ts`는 응답 `data`를 변환 전에 검사하고 어긋난 위치를 `data.items[2].status` 형식으로 알린다. 기능 저장소의 오류는 서버 실패를 `cause`에 담으며, `apiErrorOf`로 꺼내 진단에 사용한다. 응답 견본은 백엔드가 보내는 형태 그대로 `tests/fixtures/api/<도메인>/`에 보관한다. `model.ts`는 화면 도메인 모델이며 서버 DTO가 아니다. 안내 확인은 현재 메모리에서 동기적으로 기록하며 향후 서버 계약이 정해지면 경계를 조정한다. 비동기 코드 검증·동의 저장·목록 조회는 `AbortSignal`을 받고, 훅은 취소되거나 이전 세션에서 늦게 도착한 응답을 반영하지 않는다. 중복 제출·저장은 동기적인 요청 잠금으로 차단한다.

목록의 표시 상태는 기능 훅에, 필터·곡별 펼침 여부·다이얼로그 표시 여부는 화면에 둔다. 파형·재생·타브는 기능별 훅과 렌더러로 연결하며 전역 상태 라이브러리는 사용하지 않는다.

`features/workspace/navigation.ts`는 허용 화면·URL 정규화·세션 표식 확인을, `useWorkspaceNavigation.ts`는 현재 화면과 history 이동을 담당한다. 설정·도움말은 기존 `WorkspaceSession`을 유지한 채 본문만 바꾼다. 지원 안내 컴포넌트는 저장소나 전송 API를 받지 않는 읽기 전용 화면이다.
