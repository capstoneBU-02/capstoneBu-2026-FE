# Earmark Frontend

음원 기반 기타 카피 보조 서비스의 프론트엔드.

## 개발환경

- Node.js 24 LTS
- npm 11
- React, TypeScript, Vite
- Oxlint, Prettier
- Husky, commitlint

의존성 버전은 `package-lock.json`으로 관리한다. 린트는 Vite 공식 템플릿의 Oxlint 구성을 사용한다.

## 실행

```bash
nvm use
npm ci
npm run dev
```

## 명령어

| 명령어                 | 기능                                                   |
| ---------------------- | ------------------------------------------------------ |
| `npm run dev`          | 개발 서버 실행                                         |
| `npm run typecheck`    | TypeScript 타입 검사                                   |
| `npm run lint`         | 코드 검사                                              |
| `npm run format`       | 코드 포맷 적용                                         |

빌드 결과는 `dist/`에 생성된다.

### 브라우저 회귀 테스트

```bash
npx playwright install chromium
npm run test:browser
```

Playwright가 `127.0.0.1:4174`에 테스트용 Vite 서버를 실행하고 Chromium 한 종류로 검증한다. 이미 설치한 Chrome을 쓰려면 `PLAYWRIGHT_CHANNEL=chrome npm run test:browser`로 실행할 수 있다. CI는 `npx playwright install --with-deps chromium` 후 같은 테스트 명령을 사용한다.

`tests/browser/`는 실제 `App`과 `useWorkspace`·`WorkspacePage`를 StrictMode에서 렌더하고 저장소 응답 시점만 제어한다. 코드 진입·온보딩 세 선택·재방문·다른 코드의 작업 격리, 미완료 안내 재개, 만료 복구, 제출·저장 중복과 늦은 응답을 검증한다. 설정과 목록의 동의 공유·필터 보존, 뒤로/앞으로 이동, 나가기 후 기록 격리, 도움말 키보드·포커스, 읽기 전용 안내와 작업 불가 상태도 확인한다. 기존 동의 창의 오류 초기화·네이티브 닫기·포커스 복귀·텍스트 드래그 회귀도 유지한다. 곡 추가는 파일 형식·길이 판정을 가짜 검사기로 제어한다. Playwright의 Chromium에는 MP4 코덱이 없을 수 있기 때문이다. 실제 `<audio>` 검사는 `tests/fixtures/media/tone-2s.mp3`(2초 사인파, ffmpeg로 생성)와 손상 파일로만 확인한다. 새 구간은 입력 검증·경계값, 생성 중 잠금·실패 후 재시도·만료, 작성 중 행의 유지·삭제, 파일 바꾸기 확인과 입력 유지 범위를 검증한다. 테스트 화면은 개발 서버 전용이며 배포 빌드에 포함되지 않는다. 실패 스크린샷·trace는 `test-results/`, HTML 결과는 `playwright-report/`에 생성된다.

## 첫 번째 구현: 내 작업 화면

Figma의 `Earmark — 기타 카피 보조 서비스 디자인 v2`를 기준으로, 작업 공간에 진입한 이후의 **내 작업 목록·빈 상태·선택 AI 활용 동의**를 구현한다. 처리 상태 필터와 곡별 목록 펼치기·접기, 동의 저장·변경을 확인할 수 있다. 생성 완료와 사용자가 확인한 카피 완료는 별도로 표시한다.

새 카피 만들기, 작업 상세, 삭제, 오디오·악보·녹음·비교는 후속 범위다. 아직 구현하지 않은 이동·작업 버튼은 비활성화되어 있다. 구현 순서와 근거는 [구현 계획](documentation/implementation-plan.md), [요구사항 검토](documentation/requirements-audit.md)를 참고한다.

## 두 번째 구현: 테스터 코드 진입과 첫 안내

기본 주소는 코드 입력 화면이다. 신규 코드는 자료·접근 안내(1/2), 선택 AI 활용 동의(2/2)를 거쳐 내 작업으로 이어진다. 안내 확인은 동의와 별도로 기록한다. 안내만 확인한 뒤 다시 진입하면 2/2부터 재개하며, 동의·거부 저장 성공 또는 명시적인 '나중에 정할게요' 선택 뒤에만 온보딩을 완료한다. '나중에'는 미선택을 유지한다. 완료한 같은 코드의 재방문은 안내를 건너뛰고 기존 작업·선택으로 돌아온다.

다음 코드만 허용하는 **메모리 목업**이다. 실제 발급 코드·인증·서버 권한 검증은 제공하지 않는다.

| 예시 코드      | 초기 상태                                              |
| -------------- | ------------------------------------------------------ |
| `EM-NEW1-0001` | 신규, 빈 작업 공간, 안내 미확인·동의 미선택            |
| `EM-7K2P-9Q4M` | 재방문, 기존 작업 4개, 안내 완료·동의 거부             |
| `EM-NEW2-0002` | 별도의 신규 빈 작업 공간, 이전 코드의 작업·선택과 분리 |

코드 allowlist는 `src/app/demoConfig.ts`의 개발용 fixture다. 모르는 코드는 차단하며 서버의 코드 형식 regex, 발급 규칙, 실패 횟수나 제한 시간은 정의하지 않는다. 제출한 코드를 URL·브라우저 저장소·콘솔에 기록하지 않고, 실제 API 요청·쿠키·토큰을 만들지 않는다. 같은 앱 수명 안에서만 코드별 작업 공간과 안내·동의 상태를 유지한다. 새로고침·새 탭에서는 예시의 초기 상태로 돌아온다. 데이터 유지·인증 보안을 검증하는 실제 서버 구현이 아니다.

업로드 이후 흐름은 아직 연결하지 않았다.

## 세 번째 구현: 설정과 도움말

사이드바 설정에서 마스킹된 테스터 코드, 현재 AI 활용 선택과 이용 안내를 확인할 수 있다. '선택하기/변경하기'는 기존 동의 창과 같은 저장소를 사용한다. 설정과 목록을 오가도 목록을 다시 조회하거나 작업 필터·곡 펼침 상태를 초기화하지 않는다. '나가기'는 코드 입력으로 돌아가 현재 세션의 요청을 취소한다. 같은 앱 메모리에 있는 코드별 자료와 동의는 유지하며, 다른 코드로 들어오면 해당 코드의 작업 공간만 표시한다.

도움말 메뉴는 자주 묻는 질문, 이용 안내 다시 보기, 문의 안내를 연다. 안내를 다시 열고 닫는 동작은 안내 확인·동의·온보딩 완료 상태를 바꾸지 않는다. 문의 채널과 개인정보 처리방침 URL은 미정이므로 가짜 연락처나 외부 링크를 넣지 않았다. **자료 삭제 요청 안내는 읽기 전용**이다. 실제 요청 전송·접수·자료 삭제·코드 차단을 수행하지 않는다.

화면 이동은 `home/settings/task/task-not-found/task-inaccessible`만 허용하고, 새 라우터 의존성 없이 브라우저 뒤로/앞으로 이동을 지원한다. URL에는 알려진 목업 선택자와 화면 종류만, `history.state`에는 현재 세션을 구분하는 무작위 표식만 기록한다. 제출 코드·동의 값·작업 데이터는 기록하지 않는다. 다른 세션의 기록은 현재 세션의 기본 화면으로 정리하며, 진입 전이나 나간 뒤에는 과거 화면 기록으로 진입을 건너뛸 수 없다. 이 처리는 실제 서버 인증·권한 검사를 대신하지 않는다.

작업 없음과 다른 작업 공간의 작업은 같은 안내를 보여 주고 '내 작업으로' 복귀한다. 참조된 작업의 식별자나 내용을 노출하지 않는다. 구현 범위와 정책 근거는 [설정·도움말 계획](documentation/settings-support-plan.md)을 참고한다.

## 네 번째 구현: 곡·구간 작업 모델과 작업 공간 이동

작업 공간은 **곡 → 구간 작업** 구조다. 곡은 표시 이름·파일 이름·입력 종류(원곡 / 분리된 기타 음원)·길이를 가지고, 작업은 곡 id·파트·튜닝을 참조한다. 사이드바는 곡 목록을 기준으로 구간을 묶는다. 이 모델은 화면 도메인이며 API 응답 형태를 정하지 않는다.

내 작업 목록 행이나 사이드바 구간을 누르면 `?view=task&task=<작업 id>`로 이동하고, 작업 상세는 목록과 별도로 조회한다. 작업 id는 영문 소문자·숫자·하이픈 64자 이하만 허용한다. 주소로 들어온 id와 목록·사이드바에서 넘긴 id 모두 형식이 다르면 저장소에 요청하지 않고 `task-not-found` 안내로 정리한다. 없는 작업과 다른 작업 공간의 작업은 같은 오류로 처리해 같은 안내를 보여 준다. 목업은 없는 작업만 확인하며, 다른 작업 공간의 작업에 서버가 같은 오류를 응답하는지는 실제 API 연동 때 확인할 예정이다. 조회 중 다른 작업으로 이동하면 이전 요청을 취소하고 늦게 도착한 응답은 무시한다. 같은 작업을 다시 열 때도 이전 결과를 재사용하지 않고 새 조회를 기다린다. 작업 조회에서 이용 기간 종료가 확인되면 목록 조회와 같은 만료 화면으로 작업 공간 전체를 가리며, 그 뒤에 도착한 목록 응답은 만료 화면을 바꾸지 않는다. 목록을 불러오지 못해 '다시 시도'를 누르면 주소의 작업도 함께 다시 조회한다.

목록은 처음 불러온 뒤에도 서버의 작업 상태를 따라간다(#28). 탭이 다시 보이거나 창이 포커스를 되찾으면 목록을 새로 받는다. 대기·진행 중인 작업이 있는 동안에는 3초 간격의 재조회가 이어지며, 간격과 중단 규칙은 열린 작업의 재조회와 같다. 숨겨진 탭에서는 요청하지 않는다. 새 목록은 작업·곡 id별로 합치므로 펼친 곡, 선택한 작업, 포커스가 유지된다. 재조회가 실패하면 보이던 목록을 안내 없이 유지하고, 이용 기간 종료가 확인되면 만료 화면으로 바꾼다. 요청 중 화면을 떠난 구간 수정은 취소되지 않고 그 결과가 목록에 들어온다. 열린 작업 화면은 목록의 상태가 자기와 다르면 작업을 다시 조회한다. 3초는 임시값이며 서버의 상태 알림 제공 여부가 정해지면 다시 정할 예정이다.

작업 공간에는 곡 / 구간 경로, 구간 이름·처리 상태, 범위·파트·튜닝, 입력 종류만 표시한다. 파형·타브·비교와 내려받기·녹음·구간 수정·카피 완료 표시는 아직 연결 전이라고 안내하며 버튼으로 제공하지 않는다. 하단 플레이어 바는 실제 재생을 구현하는 단계(#16)에서 추가한다.

## 다섯 번째 구현: 곡 추가와 음원 파일 검사

사이드바의 `+`, 빈 화면의 '파일 선택', 빈 화면 카드에 끌어다 놓은 파일로 곡 추가 창을 연다. 놓을 수 없는 곳으로 파일을 끌면 커서가 놓을 수 없음을 표시한다. 입력 종류(원곡 / 분리된 기타 음원)와 파일 하나를 고르면 브라우저 안에서 형식과 길이를 확인한다. 파일은 전송하지 않는다. '다음'을 누르면 목업 저장소가 곡을 현재 세션 메모리에 추가하고 `?view=new-section&song=<곡 id>`로 이동해 바로 구간을 정한다.

- 확장자와 MIME을 함께 확인한다. MIME이 비어 있거나 `application/octet-stream`이면 확장자로 판단한다. 허용 형식이 아니면 디코딩하지 않고 형식 오류를 보여 준다.
- 길이는 `<audio>` 메타데이터로 읽는다. 재생할 수 없으면 손상 파일 안내를 보여 준다. 제한 시간 안에 읽지 못하면 시간 초과 안내와 '다시 확인'을 보여 주며, 같은 파일의 길이를 다시 읽는다. 길이는 초 단위로 내림해 비교하므로 05:00으로 표시되는 파일은 통과한다. 확인에 쓴 object URL은 결과와 관계없이 바로 해제한다.
- MP4는 오디오 트랙 유무를 직접 확인하지 않고, 브라우저가 메타데이터를 읽을 수 있는지로 판단한다. 영상만 있는 MP4가 통과할 수 있고, 브라우저 코덱 지원에 따라 결과가 달라질 수 있다.
- 브라우저는 MIME을 대개 확장자로 정한다. 그래서 다른 형식 파일의 확장자만 `.mp3`로 바꾸면, 브라우저가 재생할 수 있는 한 통과한다. 가변 비트레이트 MP3의 길이는 메타데이터 시점의 추정값이라 5분 경계 근처에서 몇 초 어긋날 수 있다. 클라이언트 검사는 빠른 안내용이며 최종 판정은 서버가 다시 한다. 목업 저장소도 형식과 길이를 다시 확인한다. 서버 검증 정책이 정해지면 다시 맞춘다.
- 일부 모바일 브라우저는 문서에 붙지 않은 미디어의 `preload`를 무시할 수 있어, 길이 확인은 `load()`를 직접 호출해 시작한다. iOS Safari 실기기 동작은 아직 확인하지 않았다.
- 오류 파일은 '다음'으로 진행할 수 없고 '파일 바꾸기'로 다시 고른다. 길이 확인 시간 초과는 '다시 확인'으로 같은 파일을 다시 확인할 수도 있다. 여러 파일을 한꺼번에 놓으면 하나만 올리라고 안내한다. 창을 닫으면 선택한 파일과 입력 종류를 버리고 창을 연 버튼으로 포커스를 돌려준다. 모바일 서랍에서 열었다면 메뉴 버튼으로 돌려준다. 추가 중에는 창을 닫을 수 없고, 실패하면 선택을 유지한 채 다시 시도할 수 있다.
- 허용 형식·최대 길이·확인 제한 시간은 `src/features/add-song/uploadPolicy.ts` 한 곳에 둔다. 안내 문구와 파일 선택 창의 `accept`도 이 설정에서 만든다. 5분 제한과 형식 목록은 디자인 기준 임시값이며 확정 정책이 아니다.
- 화면 밖에 떨어진 파일은 브라우저가 열지 않도록 막는다. 세션이 메모리에만 있어 페이지를 벗어나면 작업 공간이 사라지기 때문이다.

## 여섯 번째 구현: 새 구간 입력과 검증

사이드바 곡 아래의 '구간 추가'나 곡 추가 직후 새 구간 화면이 열린다. 이름(정해진 이름 + 번호), 시작·끝(`00:00.0`), 파트(리듬 / 리드 기타), 튜닝을 정하고 '타브 만들기'를 누르면 목업 저장소가 '대기' 상태의 작업을 만들고 그 작업 공간으로 이동한다. 시작·끝은 직접 입력하거나 파형에서 끌어 정한다.

- `0 ≤ 시작 < 끝 ≤ 곡 길이`이고 구간 길이가 최대 길이 이하일 때만 제출할 수 있다. 시간 형식, 끝이 시작보다 앞섬, 곡 길이 초과, 최대 길이 초과를 각각 다른 문구로 알린다. 오류는 아이콘과 문장으로 입력 아래에 보이고, 해당 입력의 `aria-invalid`·`aria-describedby`로 연결한다. 오류는 입력을 벗어난 뒤나 제출을 시도한 뒤에만 보인다. 오류가 있을 때 제출하면 모든 오류를 보이고 첫 오류 입력으로 포커스를 옮긴다.
- 시간은 내부에서 0.1초 단위 정수로 다뤄 경계(예: 30.0초) 비교에 소수 오차가 없다. 입력을 벗어나면 `00:42.1` 형태로 정리한다. 곡 길이는 0.1초 단위로 내림해 끝 시간의 상한으로 쓴다.
- 전체 파형에서 끌면 새 범위를 정하고, 선택 영역 안쪽을 끌면 길이를 유지한 채 옮긴다. 경계의 핸들은 끌거나 화살표·Page Up/Down·Home·End 키로 조절하며, 확대 파형의 핸들로 세밀하게 맞춘다. 두 핸들의 안쪽 판정 영역(각 6px)보다 좁은 구간은 안쪽을 누르면 옮겨지고, 핸들은 경계 바깥쪽을 잡아 조절한다. 손가락이나 펜으로 잡은 핸들은 옆으로 6px 이상 움직인 뒤부터 따라간다. Alt·Ctrl·Meta와 함께 누른 키는 브라우저에 넘기고, 슬라이더 값은 `1분 5.8초` 형식으로 읽힌다(#16, #25).
- 번호는 같은 곡에서 쓰지 않은 가장 작은 번호를 기본값으로 채운다. 비우면 번호 없이 저장하고, 앞의 0은 무시한다(`07` → `7`). 같은 이름을 직접 다시 입력하는 것은 막지 않는다(SEG-03/04 미확정).
- 구간 수정에서 이름을 바꾸면 같은 규칙으로 새 이름의 번호를 채우고, 원래 이름으로 돌아오면 원래 번호를 되살린다. 번호는 제안한 번호이거나 원래 이름의 원래 번호일 때만 이름을 따라 바뀌며, 그 밖에 입력하거나 비운 번호는 이름을 바꿔도 유지한다. 정책에 없는 이름·파트·튜닝은 첫 항목으로 바꾸고, 원래 값을 파형 위 안내에 함께 표시한다(#29, 안내 문구는 임시).
- 작성 중인 입력은 곡별로 메모리에 보관한다. 다른 화면에 다녀와도 유지되고, 사이드바에 '새 구간' 행으로 보인다. '취소'를 누르거나 작업을 만들면 버린다. 아무것도 바꾸지 않은 화면은 떠나면 행이 사라지고, 제출을 시도해 보였던 오류도 함께 지운다. 새로고침하면 초기화된다.
- '파일 바꾸기'는 확인 창을 먼저 띄운다. 확인하면 곡 추가 창이 열리고, 새 파일을 추가하면 새 곡으로 이동한다. 이름·번호·튜닝은 유지하고 범위와 파트는 다시 고른다. 곡 추가 창은 바꾸기 전 곡의 입력 종류로 시작한다. 기존 곡과 이미 만든 작업은 그대로 남는다(IN-05 미확정, 새 곡으로 추가하는 방식을 임시로 택함). 확인 창이나 곡 추가 창을 닫으면 입력이 그대로이고 포커스는 '파일 바꾸기'로 돌아온다.
- 만드는 중에는 입력과 '취소'·'파일 바꾸기'를 잠그고 중복 제출을 막는다. 실패하면 입력을 유지한 채 안내하고, 제출한 입력이나 버튼으로 포커스를 돌려줘 바로 다시 시도할 수 있다. 만드는 동안 연 곡 추가·도움말 창은 새 작업으로 이동해도 닫지 않는다. 화면을 떠나면 요청을 취소하므로, 응답을 기다리는 앞 요청이 있어도 다른 곡의 새 구간은 바로 보낸다. 실제 API에서는 취소 전에 서버가 이미 작업을 만들었을 수 있으므로, 같은 요청의 중복 생성을 막는 방법(멱등 키 등)을 API 계약에서 정해야 한다. 이용 기간이 끝났다는 응답이면 만료 화면으로 바꾸고 포커스를 본문으로 옮긴다.
- 최대 길이·이름 목록·번호 범위·파트·튜닝은 `src/features/new-section/sectionPolicy.ts` 한 곳에 둔다. 화면 문구와 목업 저장소 검사도 이 설정을 따른다. 목업 저장소는 0.1초 단위가 아닌 시간을 반올림하지 않고 거부한다. 최대 30초(D11)와 튜닝 3종(IN-04)은 디자인 기준 임시값이며, 최소 길이는 아직 정하지 않아 0.1초부터 허용한다.
- 새 작업의 '대기' 상태는 회색 점으로 표시하고 '진행 중' 필터에 포함한다. 작성 중인 새 구간 행은 회색 테두리 점으로 구분한다.

`view`만으로 코드 진입·온보딩을 우회할 수 없다. 직접 미리보기는 명시적인 개발용 `demo` 선택자를 함께 사용한다. 새 세션에서 이전 세션의 브라우저 기록을 만나면 기본 화면을 표시한다.

진입 오류는 허용 코드를 입력한 뒤 다음 fixture 쿼리로 확인한다.

| URL 쿼리                  | 상태                                                         |
| ------------------------- | ------------------------------------------------------------ |
| `?access=invalid`         | 무효 코드 응답                                               |
| `?access=code-expired`    | 코드 사용 기간 만료. 세션 만료 배너와 구분                   |
| `?access=revoked`         | 코드 사용 중지                                               |
| `?access=limited`         | 첫 응답에서 제한 상태. 명시적인 '다시 확인' 후 정상 응답     |
| `?access=network`         | 코드 확인 실패, 입력 수정·재시도 가능                        |
| `?access=session-expired` | 세션 만료 안내 배너, 허용 코드로 다시 진입 가능              |
| `?access=consent-error`   | 온보딩 동의 저장 실패. 2/2 유지, '나중에'로 미선택 진행 가능 |

제한 fixture는 서버 제한 응답과 해제 응답을 재현한다. 클라이언트의 실제 실패 횟수 누적·타이머·자동 해제 정책은 구현하지 않는다. 다른 오류 fixture는 해당 오류를 반복해서 보여 주며 새로고침하면 초기 상태로 돌아온다.

조회·저장에는 짧은 고정 지연을 두어 로딩과 저장 중 상태도 확인할 수 있다. 목업 데이터는 네트워크 요청이나 브라우저 저장소를 사용하지 않는다. 동의 선택은 현재 앱의 메모리에만 남고 새로고침하면 해당 fixture 초기값으로 돌아온다. 동의를 거부해도 목록 사용을 제한하지 않는다. fixture 작업은 처음 상태를 유지한다. 세션에서 만들거나 바꾼 작업만 목업 대기열에 따라 대기, 기타 분리, 타브 생성, 완료 순으로 진행한다. 실제 AI 처리는 수행하지 않는다.

`src/app/demoConfig.ts`의 보관 기간·테스터 코드 형식과 `uploadPolicy.ts`의 업로드 제한은 디자인 확인을 위한 임시 값이다. 제품 정책이나 API 명세의 확정값이 아니다.

### 디자인 폰트

Figma에서 확인한 Noto Sans KR 400·500·700(UI), JetBrains Mono 400·500·700(시간·코드·타브 숫자), Geist 600(로고)을 로컬 WOFF2로 제공한다. Figma에서는 글꼴 이름과 굵기를 확인했고, 폰트 파일은 공식 Google Fonts 배포본을 사용한다. 세 글꼴은 SIL OFL 1.1로 배포된다.

Noto Sans KR은 한글 완성형 11,172자와 자모·라틴을 포함하는 공식 유니코드 부분집합을 유지한다. `unicode-range`에 따라 화면에 필요한 파일만 요청하며, 전체 한글 파일을 미리 내려받지 않는다. JetBrains Mono와 Geist는 현재 사용 범위인 라틴 부분집합만 포함한다. `font-display: swap`으로 글자가 보이지 않는 대기를 피하고, 기존 고정 줄 높이를 유지한다. 폰트 요청은 모두 앱과 같은 출처로 향하며 런타임 Google Fonts 요청은 없다.

글꼴 출처·굵기·용량·검증 방법은 [폰트 출처](src/assets/fonts/SOURCES.md), 파일별 원본 URL과 SHA-256은 [폰트 목록](src/assets/fonts/sources.json)에 기록한다. 배포물에는 `public/fonts/`의 라이선스 원문을 함께 포함한다.

### API 연결 경계

`src/features/access/repository.ts`의 `AccessRepository`는 코드 검증·진입 결과·안내 확인·온보딩 완료를, `src/features/workspace/repository.ts`의 `WorkspaceRepository`는 목록·작업 조회, 동의 저장, 곡 추가, 구간 작업 생성·변경, 멈추기, 다시 시도, 원곡·분리 기타 음원 불러오기를 담당한다. 현재 `App.tsx`에서 목업을 주입한다. 세션이 열린 뒤에만 `WorkspaceSession`을 마운트하며, 온보딩과 목록에서 같은 작업 공간 저장소를 사용한다. 목록에서 바꾼 동의도 같은 코드의 다음 진입 결과에 반영한다.

API 확정 후 실제 저장소와 응답 변환을 연결한다. `model.ts`는 화면 도메인 모델이며 서버 DTO가 아니다. 안내 확인은 현재 메모리에서 동기적으로 기록하며 향후 서버 계약이 정해지면 경계를 조정한다. 비동기 코드 검증·동의 저장·목록 조회는 `AbortSignal`을 받고, 훅은 취소되거나 이전 세션에서 늦게 도착한 응답을 반영하지 않는다. 중복 제출·저장은 동기적인 요청 잠금으로 차단한다.

목록의 표시 상태는 기능 훅에, 필터·곡별 펼침 여부·다이얼로그 표시 여부는 화면에 둔다. 미디어 렌더러와 전역 상태 라이브러리는 이번 범위에 추가하지 않는다.

`features/workspace/navigation.ts`는 허용 화면·URL 정규화·세션 표식 확인을, `useWorkspaceNavigation.ts`는 현재 화면과 history 이동을 담당한다. 설정·도움말은 기존 `WorkspaceSession`을 유지한 채 본문만 바꾼다. 지원 안내 컴포넌트는 저장소나 전송 API를 받지 않는 읽기 전용 화면이다.
